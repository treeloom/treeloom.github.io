Code search for large codebases, built for LLMs and the humans working alongside them.

Treeloom indexes codebases into a structured representation that combines semantic embeddings with a graph of the code's actual relationships — calls, imports, inheritance, references. Ask "how does authentication work in this repo?" and get the right code, not a pile of grep matches and partial file reads.

Why this exists

Large codebases are hostile to LLMs.

Dumping the whole repo into context burns tokens and dilutes attention. Grep finds strings, not concepts. Standard RAG treats code like prose, which it isn't.

The problem
  • Repos are too big to fit in any usable context window.
  • Grep matches surface strings, not the concept you asked about.
  • Naive RAG cuts mid-function and loses structural meaning.
The Treeloom take

Code has structure worth preserving: an AST parsed by tree-sitter, a graph of how files and symbols relate, and semantic embeddings that capture meaning. Combine all three and retrieval becomes specific, structural, and faithful to how code actually works.

What it does

Retrieval that respects how code is written.

Parses, doesn't tokenize.

Tree-sitter produces real syntax trees for every supported language, so chunks respect function and class boundaries — never mid-statement cuts.

Builds a code graph.

Calls, imports, inheritance, and references become edges in Neo4j. Traverse from a symbol to its definition, callers, and dependencies — the way you'd actually navigate code.

Embeds with intent.

Code chunks embed for semantic search via a horizontally scalable fleet — Hugging Face TEI (CPU or CUDA), or your preferred hosted service via config.

Reranks for relevance.

A separate reranking stage refines initial retrieval, because the top embedding match isn't always the right answer.

Exposes itself to LLMs.

First-class MCP support means Claude and other MCP-capable assistants use Treeloom directly as a tool — no bespoke integration required.

Runs where you do.

Self-host the full stack with one docker compose, or scale embeddings and storage out across machines. Same codebase, both shapes.

Architecture

A small set of cooperating services.

Not a single binary. A persistent indexing queue (Postgres-backed) survives restarts during long jobs. Vectors default to Milvus, with adapters for Chroma, Qdrant, and pgvector. Embedding and reranking are served by Hugging Face TEI behind a distribution layer — or a hosted service per deployment.

What it's been tested on

From overnight on a single host to a week on the same hardware.

100 mid-to-large open-source GitHub repos across several popular languages — roughly 650,000 files in total. Initial naive indexing took an estimated week-plus. After tuning Milvus topology, embedding batch sizes, fleet size, and request distribution, the same workload finishes overnight. The scaling axis is embedding-worker parallelism; everything else stays boring.

Who it's for

Built for three audiences who keep running into the same wall.

Developers buried in a large repo

You want better code search than grep and ripgrep on codebases too big to hold in your head — without leaving your terminal or IDE.

Teams shipping coding assistants

You need to give LLMs faithful, token-efficient access to large internal codebases so the answers stop hallucinating file paths.

Anyone reverse-engineering a codebase

You want to understand how a project works without reading every file — and you'd rather start from the graph of how it's wired than a flat directory tree.
